11 templates de documentation

Pour chaque grand type de doc utile en projet logiciel, une structure prête à copier-coller et un prompt de génération à utiliser avec ton LLM préféré. Replie tout par défaut, déplie ce qui te sert.

🧭 Comment l'utiliser

Le template, c'est la trame que tu remplis à la main. Le prompt, c'est ce que tu passes à un LLM avec tes infos pour obtenir une première version. Dans les deux cas, tu finis par relire et ajuster, sinon ça reste de la doc générique.

Les indispensables projet

1 · README Point d'entrée du dépôt

Fichier (souvent Markdown) à la racine d'un projet qui explique ce qu'il fait, comment l'installer, comment l'utiliser. C'est la première chose que lit quelqu'un qui arrive sur le repo.

Template

# Nom du projet

> Phrase d'accroche : ce que fait le projet en une ligne.

## Contexte
Quel problème résout-il ? Pour qui ?

## Prérequis
- Versions de runtime / OS
- Comptes ou clés nécessaires

## Installation
```bash
git clone <repo>
cd <repo>
<commande d'install>
```

## Utilisation rapide
```bash
<commande minimale qui marche>
```

## Configuration
| Variable        | Rôle | Défaut |
|-----------------|------|--------|
| `EXAMPLE_KEY`   | …    | …      |

## Structure du dépôt
- `src/`   — code applicatif
- `docs/`  — documentation détaillée
- `tests/` — tests automatisés

## Documentation complète
Liens vers : tutoriels, guides, ADR, runbooks.

## Contribuer
Voir `CONTRIBUTING.md`. Branche, tests, format de commit.

## Licence
<SPDX-Identifier>

## Mainteneurs
- @nom — rôle

Prompt de génération

Tu es technical writer. Génère un README pour le projet <nom> dont l'objectif est <objectif>. Stack : <langages/frameworks>. Public cible : <dev / ops / utilisateur final>.

Inclus : pitch en une ligne, prérequis, installation, exemple d'usage minimal qui marche, table des variables d'environnement, structure du dépôt, liens vers la doc, mainteneurs. Style direct, impératif, pas de superlatifs. Markdown.

2 · ADR Architecture Decision Record

Fiche courte qui trace une décision structurante (choix d'outil, refactor, arbitrage). On date, on n'efface pas : si la décision change, on en ajoute une nouvelle qui annule la précédente.

Template

# ADR-NNN — <titre court de la décision>

- **Date**     : YYYY-MM-DD
- **Statut**   : Proposé | Accepté | Remplacé par ADR-XXX | Déprécié
- **Auteurs**  : @…
- **Décideurs**: @…

## Contexte
Quelle situation a déclenché la décision ?
Quelles contraintes (techniques, business, équipe) ?

## Problème
Quelle question structurante doit être tranchée ?

## Options étudiées
### Option 1 — <nom>
- ➕ Avantages
- ➖ Inconvénients
- 💰 Coût / effort

### Option 2 — <nom>
…

### Option 3 — Ne rien faire
…

## Décision
On retient **Option N** parce que …

## Conséquences
- Positives : …
- Négatives / dette acceptée : …
- Actions de suivi : …

## Références
Liens vers issues, RFC, benchmarks, autres ADR.

Prompt de génération

Tu rédiges une ADR sur <décision>. Contexte fourni : <contraintes, équipe, stack>. Options envisagées : <liste>. Décision retenue : <option>.

Format Michael Nygard. Date du jour. Liste explicitement avantages/inconvénients par option, y compris « ne rien faire ». Sépare clairement décision et conséquences (positives + dette acceptée). Pas de langage promotionnel, ton factuel.

3 · Runbook Procédure d'incident pas-à-pas

Procédure d'intervention pas-à-pas pour un type d'incident donné. Doit être utilisable sous stress, à 3h du matin. Pas de « ça dépend ».

Template

# Runbook — <type d'incident>

- **Sévérité**    : SEV-1 / SEV-2 / SEV-3
- **Service**     : <nom>
- **Owner**       : équipe @…
- **Dernière vérif** : YYYY-MM-DD

## Symptômes
Comment l'incident se manifeste : alerte, log type, métrique.

## Pré-requis d'accès
- Accès `<console / VPN / cluster>`
- Rôles IAM : `<…>`
- Secrets dans : `<vault path>`

## Diagnostic — checklist 5 min
1. Vérifier `<dashboard>` → seuil attendu : …
2. Logs récents : `<commande / requête>`
3. Statut dépendances aval : `<liste>`

## Actions correctives
### Cas A — <hypothèse 1>
```bash
<commande exacte, copiable>
```
Effet attendu : …
Effet de bord : …

### Cas B — <hypothèse 2>
…

## Si rien ne marche
- Escalade : @oncall-N+1, canal `#incident`
- Rollback : `<procédure / commande>`
- Communication : statut page, template message

## Post-incident
- Ouvrir un post-mortem si SEV-1/2
- Mettre à jour ce runbook si nouveau cas

Prompt de génération

Tu écris un runbook pour <type d'incident> sur le service <nom>. Public : oncall réveillé à 3h.

Contraintes : chaque commande copiable telle quelle, effet attendu explicité, pas de « il suffit de ». Inclus : symptômes observables, prérequis d'accès, diagnostic en 5 min max, actions correctives par hypothèse, condition d'escalade, procédure de rollback. Style impératif, phrases courtes, zéro ambiguïté.

4 · Post-mortem Analyse à froid d'un incident

Analyse blameless après un incident majeur : ce qui s'est passé, cause racine, ce qu'on améliore. On vise les systèmes et processus, pas les personnes.

Template

# Post-mortem — <incident> du YYYY-MM-DD

- **Statut**     : Draft | Revu | Publié
- **Sévérité**   : SEV-N
- **Durée d'impact** : HH:MM → HH:MM (UTC) — XX min
- **Auteur**     : @…

## Résumé exécutif
3 lignes max : ce qui s'est passé, l'impact, ce qu'on change.

## Impact
- Utilisateurs touchés : <volume>
- Fonctionnalités dégradées : …
- Pertes (revenus, SLA, données) : …

## Timeline (UTC)
| Heure | Événement |
|-------|-----------|
| HH:MM | Déploiement de … |
| HH:MM | Première alerte sur … |
| HH:MM | Identification cause racine |
| HH:MM | Mitigation appliquée |
| HH:MM | Service rétabli |

## Cause racine
Analyse technique. Aller au-delà des « 5 why » si nécessaire.

## Ce qui a bien fonctionné
- …

## Ce qui a moins bien fonctionné
- …

## Facteurs aggravants
Pourquoi l'incident a duré / s'est propagé.

## Actions correctives
| # | Action | Type | Owner | Échéance |
|---|--------|------|-------|----------|
| 1 | … | Préventif/Détection/Mitigation | @… | YYYY-MM-DD |

## Leçons apprises
Ce qui change durablement dans nos systèmes/process.

Prompt de génération

Rédige un post-mortem blameless pour l'incident <résumé> survenu le <date>. Données fournies : timeline brute, alertes déclenchées, mitigation.

Règles : aucun nom associé à une faute, focus systèmes et processus, distinguer cause racine et facteurs aggravants. Inclus : résumé exécutif 3 lignes, impact chiffré, timeline UTC, ce qui a marché, ce qui n'a pas marché, actions correctives avec owner et échéance. Ton neutre, factuel.

5 · Changelog Journal des versions

Journal chronologique des modifications. Format Keep a Changelog + versions SemVer. Une ligne par changement, point de vue utilisateur.

Template

# Changelog

Toutes les modifications notables figurent ici.
Format : Keep a Changelog, versions SemVer.

## [Non publié]
### Ajouté
- …

## [1.4.0] — 2026-04-15
### Ajouté
- Nouveau endpoint `/v2/users` paginé.
### Modifié
- Le champ `created_at` retourne désormais l'ISO 8601 UTC.
### Déprécié
- `/v1/users` — sera retiré en 2.0.0.
### Retiré
- Support Node 16.
### Corrigé
- Crash sur upload > 10 Mo (#412).
### Sécurité
- CVE-2026-XXXX corrigée.

## [1.3.2] — 2026-03-01
### Corrigé
- …

Prompt de génération

À partir des commits/PR fournis <liste>, génère une entrée de changelog pour la version <X.Y.Z> datée <YYYY-MM-DD>.

Format Keep a Changelog avec sections : Ajouté, Modifié, Déprécié, Retiré, Corrigé, Sécurité (n'inclure que celles non vides). Une ligne par changement, point de vue utilisateur (pas « refacto interne »). Mentionne les breaking changes en haut. Ignore les commits de pure maintenance interne.

Fiabilité & SRE

6 · Plan de monitoring « Est-ce que ça va ? »

Plan des indicateurs surveillés en temps réel et des alertes associées. Répond à « est-ce que le système va bien là, maintenant ? ».

Template

# Plan de monitoring — <service>

- **Owner**      : équipe @…
- **Criticité**  : tier 1 / 2 / 3
- **Mis à jour** : YYYY-MM-DD

## Périmètre
Quel(s) service(s), quelle(s) dépendance(s) sont surveillés.

## Indicateurs (RED ou USE)
| Indicateur            | Source                | Warn   | Crit  | Fenêtre |
|-----------------------|-----------------------|--------|-------|---------|
| Taux d'erreur HTTP 5xx| `http_requests_total` | > 1 % | > 5 %| 5 min   |
| Latence p95           | …                     | > 300 ms | > 1 s | 5 min |
| Saturation CPU        | …                     | > 70 %| > 90%| 10 min  |

## Alertes
| Nom              | Condition | Sévérité | Destinataire | Runbook |
|------------------|-----------|----------|--------------|---------|
| `HighErrorRate`  | …         | SEV-2    | PagerDuty    | runbook-errors.md |

## Dashboards
- URL principale : …
- Vues : santé globale, par endpoint, par dépendance.

## Politique de revue
- Audit trimestriel des seuils
- Suppression des alertes < 1 déclenchement actionnable / mois

Prompt de génération

Tu rédiges le plan de monitoring du service <nom> (<rôle métier>). Stack télémétrie : <Prometheus, Datadog, …>.

Pour chaque endpoint/composant critique, propose les indicateurs RED (Rate, Errors, Duration) ou USE (Utilization, Saturation, Errors), avec seuils warn/crit justifiés et fenêtre d'évaluation. Pour chaque alerte : sévérité, destinataire, runbook lié. Exclus toute alerte non actionnable.

7 · Stratégie d'observabilité « Pourquoi ça se comporte comme ça ? »

Capacité à comprendre pourquoi le système se comporte comme il se comporte, à partir de logs, métriques et traces. Va au-delà du monitoring.

Template

# Observabilité — <produit/plateforme>

## Objectif
Pouvoir répondre à n'importe quelle question sur le comportement
du système en production en moins de N minutes.

## Les trois piliers
### Logs
- Format : JSON structuré
- Champs obligatoires : `timestamp`, `level`, `service`,
  `trace_id`, `user_id` (hashé)
- Backend : <Loki / ELK / …>
- Rétention : <durée>

### Métriques
- Convention : `<service>_<objet>_<unité>_total`
- Cardinality budget : max N labels
- Backend : <Prometheus / …>

### Traces
- Standard : OpenTelemetry
- Échantillonnage : tail-based, 100 % sur erreurs, 5 % sinon
- Backend : <Tempo / Jaeger / …>

## Corrélation
Tout log/métrique/trace partage `trace_id`.
Lien depuis dashboards vers traces, depuis traces vers logs.

## Conventions de code
- SDK utilisé : …
- Helpers : `lib/observability/*`
- À ne PAS logger : PII brutes, secrets, payloads complets

## Coûts
- Budget mensuel cible : …
- Leviers : rétention, échantillonnage, cardinality.

Prompt de génération

Rédige la stratégie d'observabilité pour <produit> (stack <…>). Couvre les trois piliers logs / métriques / traces : format, conventions de nommage, backend, rétention, échantillonnage, corrélation par trace_id.

Précise ce qu'on ne logue jamais (PII, secrets). Donne les conventions de code (SDK, helpers, exemples) et les leviers de maîtrise des coûts. Style normatif (MUST / SHOULD / MAY).

8 · SLA Engagement contractuel

Engagement de niveau de service signé avec le client (ex : 99,9 % de disponibilité), avec pénalités si non tenu.

Template

# Service Level Agreement — <service>

- **Parties**            : <fournisseur> ↔ <client>
- **Période contractuelle** : YYYY-MM-DD → YYYY-MM-DD
- **Version**            : 1.0

## Périmètre
Service(s) couverts, environnements (prod uniquement, généralement).

## Engagements
| Métrique           | Engagement | Mesure                     | Période  |
|--------------------|------------|----------------------------|----------|
| Disponibilité      | ≥ 99,9 %   | ping `/healthz` toutes 60s | mois cal.|
| Latence p95        | ≤ 500 ms   | RUM côté client            | mois cal.|
| RTO incident SEV-1 | ≤ 4 h      | …                          | par incident |

## Exclusions
- Maintenances planifiées annoncées ≥ 7 j à l'avance
- Force majeure
- Indisponibilité due au client (config, quotas)

## Mesure et reporting
Source de vérité : `<outil>`. Rapport mensuel envoyé le 5 du mois.

## Pénalités
| Disponibilité mesurée    | Crédit |
|--------------------------|--------|
| < 99,9 % et ≥ 99,0 %  | 10 %   |
| < 99,0 %              | 25 %   |

## Procédure de réclamation
Délai, format, contact.

## Révision
Revue annuelle conjointe.

Prompt de génération

Tu rédiges un SLA entre <fournisseur> et <client> pour le service <nom>. Engagements à cadrer : disponibilité, latence, temps de rétablissement.

Inclus : périmètre précis, méthode de mesure et source de vérité, exclusions (maintenance, force majeure, faute client), grille de pénalités/crédits, procédure de réclamation, modalités de révision. Style juridico-technique, sans ambiguïté, chaque seuil chiffré.

9 · SLO Objectif interne mesurable

Objectif de niveau de service interne, plus strict que le SLA pour se garder de la marge. Pilote la priorisation produit/fiabilité via l'error budget.

Template

# SLO — <service / user journey>

- **Owner**       : équipe @…
- **Date d'effet**: YYYY-MM-DD
- **Revue**       : trimestrielle

## SLI (indicateur)
- **Définition** : proportion de requêtes `GET /api/v1/*`
  retournant 2xx ou 3xx en < 300 ms.
- **Source**     : `<Prometheus query>`
- **Exclusions** : requêtes synthétiques, requêtes du client `<…>`.

## SLO (cible)
- **Objectif**   : 99,5 % sur 28 jours glissants.
- **Justification** : SLA contractuel à 99,0 %, marge 0,5 pt.

## Error budget
- Budget mensuel : 0,5 % × requêtes/mois ≈ N requêtes
- Politique :
  - < 50 % consommé : développement nominal
  - 50–100 % : freeze releases non critiques
  - > 100 % : focus 100 % fiabilité jusqu'au reset

## Alertes burn-rate
| Vitesse | Fenêtre | Sévérité |
|---------|---------|----------|
| 14,4×   | 1 h     | page     |
| 6×      | 6 h     | ticket   |
| 1×      | 3 j     | revue hebdo |

## Historique
| Période  | Atteint ?  | Commentaire |
|----------|------------|-------------|
| 2026-Q1  | ✅ 99,67 % | …           |

Prompt de génération

Tu définis un SLO pour <service / user journey>. Données : trafic mensuel <…>, SLA contractuel <…>, latence cible métier <…>.

Produis : un SLI précisément défini avec sa requête de mesure, une cible chiffrée justifiée, l'error budget calculé, une politique de consommation à 3 paliers, des alertes burn-rate multi-fenêtre style Google SRE, un planning de revue. Le SLO doit être plus strict que le SLA.

10 · SRE Handbook Charte d'équipe SRE

Charte de l'équipe Site Reliability Engineering : mission, principes, périmètre d'engagement et pratiques. Issu des méthodes Google.

Template

# SRE Handbook — <organisation>

## Mission
Rendre les systèmes plus fiables, scalables et maintenables
en appliquant des méthodes d'ingénierie aux problèmes d'exploitation.

## Principes
1. L'erreur est systémique, pas humaine.
2. On automatise la toil > 50 % du temps SRE.
3. Les SLO pilotent la priorisation produit/fiabilité.
4. Tout incident SEV-1/2 → post-mortem blameless publié.

## Périmètre d'engagement
- Services on-call : <liste>
- Services en advisory uniquement : <liste>

## Pratiques
### Oncall
- Rotation : N personnes, semaine glissante
- Compensation : …
- Outillage : PagerDuty + runbooks

### Toil budget
- Max 50 % par ingénieur SRE
- Mesuré chaque sprint

### Production Readiness Review (PRR)
Checklist obligatoire avant qu'un service entre en oncall SRE.

### Game days
Fréquence : trimestrielle. Format : injection de panne contrôlée.

## Métriques d'équipe
- MTTD, MTTR par sévérité
- % temps en toil
- SLO atteints / total

## Ressources
- Runbooks : `runbooks/`
- ADR : `docs/adr/`
- Post-mortems : `docs/postmortems/`

Prompt de génération

Tu rédiges le handbook SRE de <organisation>. Couvre : mission, principes (incluant blameless, toil < 50 %, SLO comme arbitre), périmètre des services oncall vs advisory, pratiques (oncall, toil budget, PRR, game days), métriques d'équipe, liens vers runbooks/ADR/post-mortems.

Inspiration : SRE Book de Google, mais adapté à une équipe de <taille>. Ton normatif, exemples concrets, pas de jargon non défini.

11 · Diátaxis — 4 types de doc, 4 prompts

Le framework Diátaxis sépare la doc en 4 types selon leur objectif. Chaque type a sa logique propre — les mélanger dans un même document est la première cause de doc inutile.

Tutoriel

Apprendre en faisant. Pas-à-pas main dans la main, un seul chemin qui marche.

Guide pratique

Résoudre un problème précis. Pour quelqu'un qui a déjà les bases.

Explication

Comprendre. Le pourquoi, les choix, les compromis. Pas d'action.

Référence

Chercher une info précise. Descriptif neutre, exhaustif, scannable.

11a · Tutoriel Apprendre en faisant

Template

# Tutoriel — <ce que l'apprenant saura faire à la fin>

## Ce que vous allez construire
Capture d'écran ou résultat final.

## Prérequis
- … (le minimum strict)

## Étape 1 — <action>
```bash
<commande>
```
Vous devriez voir : `<sortie attendue>`

## Étape 2 — …

…

## Vous y êtes arrivé
Récapitulatif de ce qui a été appris. Pas de digression.

## Pour aller plus loin
Lien vers les guides « comment faire X ».

Prompt de génération

Rédige un tutoriel Diátaxis pour apprendre <compétence>. Public : débutant complet sur <sujet>.

Règles strictes : (1) main dans la main, l'apprenant tape exactement ce qui est écrit ; (2) chaque étape produit un résultat observable, mentionné explicitement ; (3) pas d'options, pas d'alternatives, un seul chemin qui marche ; (4) zéro explication conceptuelle ; (5) finir par un récap concret. Ton encourageant, deuxième personne (« vous »).

11b · Guide pratique (how-to) Résoudre un problème précis

Template

# Comment <accomplir une tâche précise>

## Quand utiliser ce guide
Situation concrète où ce guide s'applique.

## Prérequis
Ce que vous devez déjà avoir/savoir.

## Procédure
1. <étape>
2. <étape>
3. <étape>

## Variantes
- Si `<condition A>` : faire `<…>`
- Si `<condition B>` : faire `<…>`

## Vérification
Comment savoir que c'est réussi.

## Voir aussi
- Référence : <lien>
- Tutoriel d'introduction : <lien>

Prompt de génération

Rédige un guide pratique Diátaxis : « Comment <tâche précise> ». Public : utilisateur qui a déjà les bases et fait face à ce problème en situation réelle.

Règles : (1) orienté tâche, pas apprentissage ; (2) suppose les bases, ne ré-explique pas ; (3) inclut les variantes selon le contexte ; (4) ne décrit que les étapes nécessaires à cette tâche ; (5) ne fait pas la promotion d'une approche, ne digresse pas. Style impératif, court.

11c · Explication Comprendre le pourquoi

Template

# <Concept> — explication

## De quoi parle-t-on
Définition courte.

## Pourquoi ça existe
Quel problème ce concept résout.
Contexte historique si pertinent.

## Comment ça fonctionne
Modèle mental. Schémas. Analogies.

## Compromis et alternatives
- Alternative A — quand la préférer
- Alternative B — pourquoi on ne l'a pas choisie

## Limites
Ce que ce concept ne résout pas, idées fausses fréquentes.

## Pour creuser
Lectures, papers, ADR liés.

Prompt de génération

Rédige une explication Diátaxis sur <concept>. Public : praticien qui sait s'en servir mais veut comprendre pourquoi.

Règles : (1) orienté compréhension, pas action — aucune procédure pas-à-pas ; (2) éclaire les choix, le contexte, les compromis ; (3) compare aux alternatives et dit pourquoi on a choisi celle-ci ; (4) nomme les limites et idées fausses ; (5) peut être lu sans terminal ouvert. Ton réflexif, exemples illustratifs autorisés.

11d · Référence Chercher une info précise

Template

# Référence — <module / API / commande>

## Synopsis
```
<signature ou usage en une ligne>
```

## Description
1 à 3 phrases factuelles.

## Paramètres
| Nom   | Type   | Requis | Défaut | Description |
|-------|--------|--------|--------|-------------|
| `foo` | string | oui    | —      | …           |
| `bar` | int    | non    | `0`    | …           |

## Retour
Type, structure, valeurs possibles.

## Erreurs
| Code   | Cause |
|--------|-------|
| `E001` | …     |

## Exemple minimal
```bash
<exemple court, sans contexte narratif>
```

## Voir aussi
Symboles liés.

Prompt de génération

Rédige une référence Diátaxis pour <API / commande / module>. Public : développeur qui sait ce qu'il cherche et veut une réponse rapide.

Règles : (1) descriptif neutre, pas pédagogique ; (2) exhaustif sur les paramètres, types, valeurs par défaut, retours, codes d'erreur ; (3) un exemple minimal par entrée, sans narration ; (4) structure plate et scannable, tableaux privilégiés ; (5) zéro opinion, zéro tutoriel embarqué. Style télégraphique, présent.

À toi de jouer

Choisis le template qui te manque le plus, copie-le dans ton outil, remplis-en au moins 50 %. Mieux vaut un README à moitié rempli qu'un dépôt sans README.
