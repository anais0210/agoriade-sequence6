## Séquence 3 — Pratique 1 : Écrire la doc technique de ton projet

| Champ Modulo | Valeur |
|---|---|
| **Titre** | Pratique 1 — Doc technique de ton projet |
| **Durée** | 40 min |
| **Heure** | 9h35 |
| **Format** | Individuel + coaching |
| **Type** | Pratique guidée |

**Objectif pédagogique**
Démarrer ou rattraper la doc technique de son projet avec une trame éprouvée. Sortir avec un document utilisable.

**Instructions animateur**
1. Distribuer la trame (3 min).
2. Rappel 6 blocs (5 min) : vue d'ensemble, stack, comptes/accès, flux données, procédures, décisions (ADR).
3. Rédaction individuelle (25 min) : coaching circulant.
4. Mise en commun (7 min) : 2-3 volontaires partagent leur bloc le mieux rempli.

**Notes**
Piège : vouloir tout remplir parfaitement. Pousser à « version 1 suffisante » — imparfaite mais existante. Mieux vaut blocs 2 et 3 bien faits que tout bâclé.

## Séquence 6 — Pratique 2 : Écrire ton premier runbook

| Champ Modulo | Valeur |
|---|---|
| **Titre** | Pratique 2 — Ton premier runbook d'incident |
| **Durée** | 60 min |
| **Heure** | 10h55 |
| **Format** | Individuel puis binôme |
| **Type** | Pratique guidée |

**Objectif pédagogique**
Produire un runbook complet et testable pour un scénario d'incident réaliste sur son projet.

**Instructions animateur**
1. Distribuer template (3 min).
2. Poser le scénario (5 min) : choisir parmi 4 scénarios (Make en panne 23h dim / Airtable corrompue / clés API fuitées / user bloqué).
3. Rédaction (35 min) : remplir le template, coaching circulant.
4. Test en binôme (10 min) : échange de runbooks, l'autre essaie de jouer l'incident.
5. Corrections (7 min) : améliorer avec retours.

**Notes**
Le test croisé est LE moment d'apprentissage — beaucoup découvriront des trous. Pousser les paires à être rigoureuses, pas gentilles.
