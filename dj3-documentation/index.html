Séquence 1 · 9h00 · 15 min

Inclusion — « La doc de l'enfer »

🎯 Objectif

Ouvrir la matinée par l'expérience partagée : tout le monde a vécu une doc absente, obsolète ou inutilisable. Récolter ces anecdotes pour ancrer pourquoi on va faire différemment.

Consignes animation

  1. Accueillir (2 min) — Nouvelle semaine, transition vers la fin de la séquence. Annoncer DJ3+DJ4 comme un binôme (matin/après-midi du 4 mai).
  2. Question brise-glace (3 min) — « Raconte une fois où tu t'es retrouvé·e bloqué·e à cause d'une doc manquante ou incompréhensible. »
  3. Tour de table (8 min) — Noter au tableau les motifs récurrents : « doc obsolète », « doc introuvable », « doc pas faite », « doc mais pas à jour »…
  4. Annoncer le cap (2 min) — « Aujourd'hui, on va construire deux choses : une trame de doc qui tient dans le temps, et un runbook qui te sauve à 23h un dimanche. »
Séquence 2 · 9h15 · 20 min

Apport 1 — Les 4 types de doc qu'il te faut

🎯 Objectif

Donner un cadre qui permet de savoir quelle doc écrire pour quel besoin : le framework Diátaxis, simplifié pour le No-Code/IA.

Contenu à transmettre

1. Pourquoi les docs échouent

Parce qu'on mélange 4 objectifs différents dans le même doc. Un utilisateur qui veut apprendre n'a pas les mêmes besoins qu'un utilisateur qui veut résoudre un problème précis. Séparer = doc utile.

2. Le framework Diátaxis — 4 types de doc

1

Tutoriel

Pour qui ? Quelqu'un qui découvre.

Objectif : apprentissage, pas à pas du début à la fin.

Exemple : « Crée ton premier scénario Make en 10 min ».

2

Guide (How-to)

Pour qui ? Quelqu'un qui sait déjà, face à un problème précis.

Objectif : résoudre une tâche ponctuelle.

Exemple : « Comment ajouter un webhook dans un scénario existant ».

3

Explication

Pour qui ? Quelqu'un qui veut comprendre « pourquoi ».

Objectif : donner le contexte, les choix, les compromis.

Exemple : « Pourquoi on a choisi Airtable plutôt que Notion ».

4

Référence

Pour qui ? Quelqu'un qui cherche une info précise, rapide.

Objectif : lookup exhaustif, structuré.

Exemple : liste des scénarios Make, des tables Airtable, des secrets API.

3. La règle d'or : commencer par la Référence

Beaucoup de projets n'ont aucune doc. Si tu dois commencer par une seule, commence par la Référence technique : inventaire des composants, des secrets, des dépendances. C'est ce qui sauve quand ça casse.

4. Où écrire la doc ?

  • Notion / Outline / Obsidian — simple, collaboratif, bon pour les projets No-Code.
  • Un README dans le repo — si tu as du code (même un peu).
  • GitBook / Mintlify — si la doc est publique / destinée aux utilisateurs.
⚠️ Le piège numéro 1

Mettre la doc dans un endroit que tu ne visites jamais. La doc doit vivre là où tu travailles — sinon elle se périmera. Le meilleur endroit, c'est celui où tu retournes tous les jours.

Séquence 3 · 9h35 · 40 min

Pratique guidée 1 — Écrire la doc technique de ton projet

🎯 Objectif

Démarrer — ou rattraper — la doc technique de son propre projet en s'appuyant sur une trame éprouvée. Sortir avec un document utilisable, pas un template vide.

Consignes animation

  1. Distribuer la trame (3 min) — Pointer la trame de doc technique No-Code/IA. Chacun·e l'ouvre dans son outil préféré (Notion, Google Doc, README).
  2. Rappeler les 6 blocs (5 min) :
    • Bloc 1 — Vue d'ensemble (1 paragraphe + schéma)
    • Bloc 2 — Stack technique (tous les outils utilisés)
    • Bloc 3 — Comptes et accès
    • Bloc 4 — Flux de données principaux (3-5 schémas)
    • Bloc 5 — Procédures courantes
    • Bloc 6 — Décisions (ADR — Architecture Decision Records)
  3. Rédaction individuelle (25 min) — Chacun·e remplit la trame sur son projet. Animation en coaching circulant.
  4. Mise en commun (7 min) — 2-3 personnes volontaires partagent leur bloc le mieux rempli et expliquent leurs choix.
💡 Pour l'animation

Le piège : vouloir tout remplir parfaitement. Pousser à « la version 1 suffisante » — imparfaite mais existante. Mieux vaut un bloc 2 et bloc 3 bien faits qu'une trame complète bâclée.

Séquence 4 · 10h15 · 25 min

Débrief + Apport 2 — Procédures de support qui tiennent

🎯 Objectif

Sortir de « la doc c'est pour les autres » et entrer dans « comment je construis les procédures qui me sauvent quand ça casse ».

Déroulé

  1. Débrief de la pratique doc (7 min) — Qu'est-ce qui a été difficile ? Qu'est-ce qui reste à faire ? Partager les blocages.
  2. Apport sur le support (18 min) — Parcourir les 3 briques ci-dessous.

Les 3 briques du support qui tient

1

Runbook d'incident

Une fiche par type de panne courante : symptôme → diagnostic → actions → qui alerter.

Exemple : « Le scénario Make ne s'exécute plus » → 1. Vérifier le statut Make → 2. Vérifier les quotas → 3. Vérifier les logs → 4. Si rien : rollback.

2

Procédure d'escalade

Qui contacter, dans quel ordre, sur quel canal, pour quel type de problème.

Exemple : Facturation OpenAI → fondateur. Bug fonctionnel → dev. Question utilisateur → support N1.

3

Post-mortem

Après chaque incident majeur : qu'est-ce qui s'est passé, qu'est-ce qu'on a appris, qu'est-ce qu'on change.

Règle : pas de blame. Le post-mortem vise les systèmes, pas les personnes.

Les 3 principes à retenir

✨ Principe 1 — Le runbook doit être utilisable à 3h du matin

Donc : pas d'ambiguïté, pas de « ça dépend », chaque étape est une action concrète avec un critère de réussite clair.

✨ Principe 2 — Le runbook doit être testé

Au moins une fois tous les 6 mois, simuler l'incident et dérouler le runbook. Si une étape ne marche pas, corriger.

✨ Principe 3 — Le runbook doit être accessible vite

Ne pas le planquer dans Notion dans un sous-sous-dossier. Un lien direct depuis un endroit que tu vas voir en panique (ton téléphone, ton bookmark, etc.).

Séquence 6 · 10h55 · 60 min

Pratique guidée 2 — Écrire ton premier runbook d'incident

🎯 Objectif

Produire un runbook complet et testable pour un scénario d'incident réaliste sur son propre projet. Sortir avec une fiche utilisable.

Déroulé

  1. Distribuer le template (3 min) — Pointer le template Runbook d'incident.
  2. Poser le scénario (5 min) — Chacun·e choisit un scénario parmi :
    • « Mon workflow Make est en panne à 23h un dimanche soir »
    • « Ma base Airtable a été corrompue ce matin »
    • « Mes clés API OpenAI ont fuité sur internet »
    • « Mon utilisateur principal me dit que rien ne marche »
  3. Rédaction (35 min) — Remplir le template pour ce scénario. Coaching circulant.
  4. Test en binôme (10 min) — Échanger son runbook avec un·e voisin·e. L'autre essaie de « jouer » l'incident avec le runbook — trouve-t-il/elle des trous ?
  5. Corrections rapides (7 min) — Corriger son runbook avec les retours reçus.
💡 Pour l'animation

Le test croisé est LE moment d'apprentissage. Beaucoup vont découvrir que leur runbook a des trous (étapes implicites, chemins non testés). C'est le but. Pousser les paires à être rigoureuses, pas gentilles.

Les livrables à emporter

Trois livrables pour documenter et sécuriser l'exploitation de ton produit.

📋 Livrable 1

Trame de doc technique No-Code/IA

Structure en 6 blocs pour documenter un produit No-Code/IA. À copier-coller dans Notion / Google Doc / README.

📦 Bloc 1 — Vue d'ensemble

  • Nom du produit : [nom]
  • Pitch en 1 phrase : [ex : « Application qui aide les RH à pré-qualifier les candidatures via IA »]
  • Utilisateurs cibles : [qui utilise, combien]
  • Fonctions principales : [liste à puces, 3-5 items]
  • Schéma d'architecture : [image ou description : frontend → backend → services tiers]

🛠️ Bloc 2 — Stack technique

CoucheOutilVersion / planRôle
Frontend / UI[ex : Softr / Bubble / Webflow][plan payé][rôle]
Base de données[ex : Airtable][plan][rôle]
Automation[ex : Make / n8n][plan][rôle]
IA / LLM[ex : OpenAI GPT-4o][version API][rôle]
Hébergement[ex : Vercel][plan][rôle]
Auth[ex : Supabase auth][plan][rôle]

🔑 Bloc 3 — Comptes et accès

  • Liste des comptes : [outil + email du compte owner + qui a accès]
  • Gestionnaire de secrets : [ex : 1Password, Bitwarden — où sont les clés API]
  • Double auth : [activée sur quels outils ? avec quel téléphone de secours ?]
  • Procédure de récupération : [si le fondateur est indisponible, comment accéder]

🌊 Bloc 4 — Flux de données principaux

Pour les 3-5 flux les plus importants, documenter :

  • Déclencheur : [ex : utilisateur soumet formulaire sur Softr]
  • Étapes : [numérotées, pas à pas]
  • Données manipulées : [quelles données, où elles vont]
  • Résultat attendu : [quoi sortie, dans quel délai]
  • Cas d'échec : [que se passe-t-il si ça rate]

📝 Bloc 5 — Procédures courantes

Comment faire les tâches récurrentes. Une fiche par tâche :

  • Ajouter un nouvel utilisateur
  • Modifier un prompt IA
  • Ajouter un champ à Airtable
  • Déployer une nouvelle version
  • Faire une sauvegarde manuelle

🧭 Bloc 6 — Décisions (ADR — Architecture Decision Records)

Une entrée par décision structurante. Pour chacune :

  • Titre : [ex : « Pourquoi Airtable plutôt que Notion »]
  • Date : [YYYY-MM-DD]
  • Contexte : [quel problème on résolvait]
  • Alternatives étudiées : [option A, option B, option C]
  • Décision retenue : [option + justification courte]
  • Conséquences : [ce que ça implique, limites connues]
🚨 Livrable 2

Template Runbook d'incident

Fiche à remplir avant l'incident. Une fiche par type de panne probable.

💡 Comment utiliser

Copie ce template dans ton wiki projet (Notion / README). Duplique la fiche pour chaque scénario d'incident identifié. Teste au moins une fois par trimestre.

📄 Template Runbook

  • Titre de l'incident : [ex : « Le scénario Make ne s'exécute plus »]
  • Dernière mise à jour : [date] — Par : [nom]
  • Dernière fois testé : [date]

🔎 Comment on sait qu'on est dans ce cas ?

Symptômes observables, dans l'ordre de probabilité :

  • [Symptôme 1 — ex : « Les emails automatiques ne partent plus depuis ce matin »]
  • [Symptôme 2]
  • [Symptôme 3]

🩺 Diagnostic (dans l'ordre)

  1. [Action de diagnostic 1 — ex : « Aller sur status.make.com — vérifier si Make a un incident » — critère de réussite : [réponse observable]]
  2. [Action de diagnostic 2 — ex : « Aller dans le dashboard Make, onglet Scenarios, vérifier si le scénario est ON et son dernier run »]
  3. [Action de diagnostic 3 — ex : « Regarder les logs du dernier run pour voir le message d'erreur »]

🛠️ Actions correctives (par ordre d'effort)

  1. [Action 1 — la plus simple, la plus rapide]
  2. [Action 2 — si la 1 ne marche pas]
  3. [Action 3 — rollback, plan B, dernier recours]

📞 Qui alerter et quand

  • Si l'action 1 résout : [qui prévenir éventuellement, ex : message Slack]
  • Si on passe à l'action 2-3 : [personne à alerter, canal]
  • Si aucune action ne résout (30 min sans solution) : [personne de dernier recours, téléphone]

🔁 Après l'incident

  • Noter l'incident dans le registre (date, cause, durée, action qui a résolu)
  • Si l'incident était nouveau : mettre à jour ce runbook
  • Si l'incident est récurrent : prévoir une vraie correction structurelle (pas juste patch)
  • Si impact utilisateur : préparer la comm (ce qu'on dit, quand, à qui)
